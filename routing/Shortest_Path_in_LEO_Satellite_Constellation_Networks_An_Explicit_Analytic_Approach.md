## 一句話摘要
在規則的 Walker 星座（每顆衛星 4 條 ISL）裡，**同軌 ISL 長度固定，跨軌 ISL 越靠近高緯度越短**。作者利用這個規律，把「找最短距離路徑（SDP）」從「建圖＋跑 Dijkstra」變成「**代一條公式**」：先算出要在哪顆衛星「轉彎」跨軌道，就直接得到整條路徑。這個演算法叫 **StepClimb**：
- **mono-valley**（起點、終點夠近）：有嚴格證明，與 Dijkstra 的誤差是 **0**。
- **bi-valley**（距離較遠）：用近似公式，平均誤差約 **0.1%**。
- 計算時間在大星座比 Dijkstra 省 **99.4% 以上**。

另一個副產品是一條直覺結論：**跨軌的 hop 會「一口氣連續做完」，而且偏好在高緯度做。**

## 0. 背景知識
### 這篇在解什麼：SDP vs MHP
- **MHP（Minimum-Hop Path，最少跳數路徑）**：從 A 到 B 跳數最少的路。在 +Grid 網格上，從 A 到 B 要走 M−1 步「同軌」（上下）和 N−1 步「跨軌」（左右）。只要不繞路，**任何先後順序**的走法跳數都一樣，所以 MHP 不只一條，而是一整塊 **M×N 的方格區域**（論文 Fig. 3、Fig. 4）。
- **SDP（Shortest-Distance Path，最短距離路徑）**：實際公里數最短的路，延遲也最低。
- 前人 [20] 證明：**幾乎所有 SDP 都落在 MHP 區域裡面**，只有少數近極軌星座有例外。所以問題縮小成：**在 M×N 方格裡，要在哪幾列做「跨軌」那 N−1 步？**

**比喻**：在棋盤狀的城市裡從左下走到右上，一定要往上走 M−1 格、往右走 N−1 格。往上的街（同軌）每段都一樣長；往右的街（跨軌）**越往北越短**（就像經線越往北越靠近）。那最省路的走法當然是：**先往北走到最窄的地方，再一口氣往右走完，再往下（或繼續往上）走到終點。**

### 衛星的「相位」u（argument of latitude）
- u = 衛星從升交點（往北穿過赤道那一點）沿軌道走了多少角度。u=0° 在赤道往北；u=90° 在最北（緯度 = 傾角 α）；u=180° 回到赤道往南；u=270° 最南。
- 它決定衛星現在在哪個緯度，也就決定了跨軌 ISL 有多長。

### Walker 星座參數（α: NP·MP/NP/F）
| 符號               | 意義                                         |
| ---------------- | ------------------------------------------ |
| α                | 軌道傾角                                       |
| NP               | 軌道面數                                       |
| MP               | 每個軌道面上的衛星數                                 |
| F                | phasing factor：相鄰軌道面的衛星錯開多少                |
| ΔΩ               | 相鄰軌道面 RAAN 差：Delta 星座是 2π/NP，Star 星座是 π/NP |
| ΔΦ = 2π/MP       | 同軌相鄰兩顆的相位差                                 |
| Δf = 2πF/(MP·NP) | 相鄰軌道面上「對應衛星」的相位差                           |

Walker Star 和 Walker Delta 的差別見 [[OPSPF_Orbit_Prediction_Shortest_Path_First_Routing_for_Resilient_LEO_Satellite_Networks]] 的背景知識。

### ISL 長度怎麼變（§III-B，Fig. 2）
- **同軌 ISL**：dV = √2·(RE+hs)·√(1−cosΔΦ)，**固定不變**（同一圈上兩顆衛星的間距固定）。
- **跨軌 ISL**：dH = √2·(RE+hs)·√(1−cosΘ)，其中 cosΘ 含有 **cos(2u+Δf)** 這一項，所以 dH 隨 u 變化：
  - 週期 π，也就是北半球、南半球各有一個「最短點」。
  - 最短點在 **Us = kπ + π/2 − Δf/2**，大約是 u ≈ 90°（最北）或 270°（最南）。
  - 最長點在赤道附近。
- 換句話說：**緯度越高，相鄰軌道越靠近，跨軌 ISL 越短。**

**小算例（我自己用論文公式 (1)–(3) 算的，類 Starlink：α=53°、550 km、72×22、F=1）**：

| 衛星相位 u | 位置 | 跨軌 ISL dH |
|---|---|---|
| 0° | 赤道 | 621 km |
| 30° | 中緯度 | 572 km |
| 60° | 較高緯度 | 459 km |
| 90° | 最北（緯度 53°） | 391 km |

同軌 ISL dV 則固定是約 1970 km。所以「在哪裡跨軌」可以讓每次跨軌差到 **200+ km**。

## 1. Problem／研究目標
- **傳統做法**：把整個星座建成一張圖 G=(V,E)，算出**每一條** ISL 的長度當 weight，再跑 Dijkstra（O(NS²)）或 Bellman-Ford（O(NS·NL)）反覆 relax。
  - 星座越大（Starlink 上千顆）越貴，而且衛星一直在動，每個瞬間都要重算。
  - 需要「全網的拓樸＋全部的 ISL 長度」才能算，不利於分散式路由。
- **論文要的**：一個**顯式解析解（explicit analytic）**。只要給星座參數、起點衛星的相位 u0、起終點相差幾列（M）幾面（N），就能**直接算出** SDP 和它的長度，不用建圖、不用迭代，複雜度 O(1)。

### 有沒有 problem formulation？
**有**，這篇和 OPSPF／StableRoute 不同，有正式的最佳化式子：
- **單谷（mono-valley）**：min Σ|ũ(vi)|，也就是「讓每次跨軌都盡量靠近最短點」。
- **雙谷（bi-valley）**：式 (21)，決策變數是 v1、R、Δv，限制式 (21b)–(21f)。

## 2. Key Idea
1. **縮小搜尋空間**：SDP ⊂ MHP 區域。所以只需要決定 N−1 次跨軌各在**第幾列 vi** 發生（v1 ≤ v2 ≤ … ≤ vN−1）。
2. **路長拆成兩塊**：d = Σ dH(第 i 次跨軌) + (M−1)·dV。後面那塊是常數，**只剩跨軌那塊要最小化**（式 (7)）。
3. **把距離換成角度**：dH 只跟「離最短點 Us 有多遠」有關。定義**相位偏移**
   ũ = mod(u + Δf/2, π) − π/2，
   問題就變成 **min Σ|ũ(vi)|**：讓所有跨軌點離「最窄處」的總角度最小。
4. **一維中位數問題**：Σ|x − 某些點| 的最小值在**中位數**取得。這是整個解析解的數學核心（Appendix A/B）。

**比喻**：一群人要在一條路上選一個集合點，讓大家走的總距離最短，答案是選在「中間那個人」的位置。這裡的「集合點」是 v1（在哪一列開始跨軌），「大家」是 N−1 個理想跨軌位置 Us, Us−Δf, Us−2Δf, …。

## 3. Method：StepClimb
### 3.1 Mono-valley（單谷）情況（§IV-B）
- 定義 **Δu = (M−1)ΔΦ + (N−1)Δf**，是 MHP 區域內所有衛星的相位跨度。
- 若 **Δu < π/2 − ũ0**，所有相關衛星都落在**同一個「谷」**裡（Fig. 5：dH 對 u 的圖像是一個 U 形，只有一個最低點）。這叫 mono-valley。
- **Proposition 1／3**：此時最佳解一定是 **v1 = v2 = … = vN−1**，也就是**所有跨軌一口氣連續做完**。
  - 直覺：如果有一次跨軌拖到後面，它就離最窄處更遠，只會更長。
- **Proposition 2／4**：v1 用一條公式直接算出：
  - v1* = (π/2 − mod(u0+Δf/2, π) − (N−2)/2·Δf) / ΔΦ + 1
  - **v1 = max{1, min{M, Round(v1*)}}**
  - 翻成白話：「從 u0 出發往上爬，爬到**最接近最窄處**的那一列就轉彎」；超出區域就夾在 1 或 M。
  - Round 剛好是 .5 時兩邊一樣好，所以 SDP 不唯一（§V-B 也觀察到）。
- **Algorithm 1**：算 Δf、ΔΩ、ΔΦ → 算 v1 → 算每個跨軌點的 u(vi) → 用公式 (1)–(3) 算距離 → 加總。
- **誤差 = 0**（有嚴格證明，也用 10⁶ 個隨機星座驗證過）。

**名字的由來（我的推測）**：路徑像「先爬（climb）到最窄處 → 一步（step）跨完所有軌道」，畫出來像一個台階。

#### Toy example：4×4 MHP 區域（同上面類 Starlink 參數，u0=40°）
要往上 3 格（同軌 3 × 1970 km 固定）、往右 3 格（跨軌，長度看在哪一列）。比較三種走法的跨軌總長：

| 走法 | 在哪幾列跨軌 (v1,v2,v3) | 三段 dH (km) | 跨軌合計 |
|---|---|---|---|
| 一出發就先往右 | (1,1,1)，u≈40° | 537, 536, 536 | 1609 km |
| 分散著走（斜斜的階梯） | (1,2,3) | 537, 472, 415 | 1424 km |
| **先往上爬到頂，再一口氣往右**（StepClimb） | **(4,4,4)**，u≈89° | 391, 391, 391 | **1172 km** |

公式算出的 v1* ≈ 4.0，所以 v1=4，和暴力列舉全部組合的結果一樣（我另外用 u0 = 0°/20°/40°/60° 驗證過，四種情況都吻合；u0=60° 時答案是 v1=3，因為第 4 列已經爬過頭了）。

### 3.2 Bi-valley（雙谷）情況（§IV-C）
- Δu 變大時，相關衛星可能跨越**兩個谷**（例如一部分在北半球最窄處附近，一部分已經繞到南半球的最窄處附近）。這時「全部集中在一處跨軌」不一定最好。
- 作者假設最佳路徑是 **bi-step path**（Fig. 7）：
  - 在第 v1 列先做 R 次跨軌；
  - 再往上走 Δv 列；
  - 在第 v1+Δv 列做剩下的 N−1−R 次跨軌。
  - 也就是兩個台階，各自落在一個谷的最低點附近。
- 寫成最佳化式 (21)：在 v1、R、Δv 上最小化總相位偏移。三個變數互相牽動，難以精確解。
- **近似解析解（式 (22)–(25)）**：
  1. 先讓兩段的「理想點」盡量重疊，得到 **Δv ≈ (π − (N−1)/2·Δf)/ΔΦ**（大約是半圈，也就是從北邊的最窄處到南邊的最窄處），**R ≈ (N−1)/2**（兩段各分一半）。
  2. 再用中位數的想法求 v1（v1**），夾在合法範圍內。
  3. 另外試「全部連續跨軌」（Δv=0、R=N−1）這個特例，兩者取較好的（Algorithm 2 第 5–9 行）。
- 這部分**沒有嚴格證明**，是近似解。

### 3.3 適用範圍（§IV-D）
- 實務上 MP、NP 有限、Δf 小，所以 Δu 不會太大，**單谷＋雙谷就涵蓋所有情況**。
- 可以用在 LEO 以外的高度，只要是 Walker＋四 ISL。
- 多殼層星座可以每一層各自用，但**跨層鏈路不行**。
- 地面站到地面站：先決定上下行接入的衛星，就能套用。
- 特例 **Δf = 0**：所有跨軌都在最窄處一口氣做完。這和常見的啟發式「在高緯度跨軌」[26][27][35] 一致，等於幫那些啟發式提供了理論依據。

## 4. Setup（§V-A）
- **Monte-Carlo**：隨機產生 **10⁶ 個星座**，參數範圍如下（Table II），並對每個星座**遍歷**所有 M、N、u0（u0 步長 0.01）。

| 參數 | 範圍 |
|---|---|
| α | 40°–70° |
| MP、NP | 4–50 |
| F | 0 ~ NP−1 |
| M | 2 ~ ⌈MP/2⌉ |
| N | 2 ~ ⌈NP/2⌉ |

- 硬體：Intel i5-1135G7、16 GB RAM（一般筆電）。
- **比較對象**：
  - 精確解：Dijkstra（全圖）、DAG（只在 MHP 子圖上的 DAG 最短路）。
  - 近似解：RandMHP（在 MHP 區域內隨機選方向）、LSP [25]（往剩餘 hop 多的方向走，避免連續長跨軌）、DisCoRoute [26]（讓跨軌發生在高緯度）。
- **真實星座**：Celestri 7×9、Iridium 6×11、OneWeb 18×36、Kuiper 34×34、Starlink-a 72×22、Starlink-b 24×66（NP×MP）。

## 5. Results
### 5.1 Mono-valley：正確性
- 10⁶ 個情境中，Dijkstra 找到的 SDP **全部**都是「跨軌連續做完」，且總相位偏移最小，驗證了 Proposition 3/4。
- StepClimb 的距離與 Dijkstra **完全相同**；路徑不同的情況是因為 SDP 本身不唯一（v1 或 v1+1 都一樣短）。

### 5.2 計算時間（Table III，每個星座 10⁶ 組起終點）

| 星座 NP×MP | 7×9 | 6×11 | 18×36 | 34×34 | 72×22 | 24×66 |
|---|---|---|---|---|---|---|
| Dijkstra | 93.1 s | 95.9 s | 351.0 s | 615.6 s | 1771.4 s | 1785.6 s |
| DAG | 8.1 s | 8.3 s | 17.0 s | 19.1 s | 26.9 s | 36.5 s |
| StepClimb | 5.0 s | 5.1 s | 7.2 s | 7.1 s | 9.5 s | 9.6 s |

- 「省 99.4%」是**最大的星座**（Starlink 24×66：1 − 9.6/1785.6 ≈ 99.5%）。小星座（7×9）大約省 94.6%。
- 對 DAG 省 64%–74%。
- **星座越大，省越多**。StepClimb 理論上是 O(1)，但時間仍略隨規模增加，這部分我推測是迴圈要算 N−1 個跨軌點，加上程式本身的固定開銷。

### 5.3 Bi-valley：準確度（Table IV）

| | RandMHP | LSP | DisCoRoute | StepClimb | StepClimb（含單谷） |
|---|---|---|---|---|---|
| MRE（平均相對誤差） | 8.82% | 8.16% | 1.1% | **0.11%** | **0.09%** |
| Max. RE | 151.39% | 145.18% | 97.31% | 7.18% | 7.32% |
| 找到最佳解的機率 | 9.67% | 23.86% | 41.88% | 77.75% | 83.38% |

- DisCoRoute 只是啟發式「選高緯度」，沒有嚴格推導，所以誤差大很多。
- Fig. 9（Starlink，M=5、N=11）：StepClimb 和 Dijkstra 的路徑形狀略不同（R 算得不準，兩段台階的分配不同），但距離只差 0.02%。兩者的跨軌都發生在高緯度。

### 5.4 不同規模的星座（Table V）
- MRE：Celestri 0、Iridium 0.10%、OneWeb 0.04%、Kuiper 0.01%、Starlink-a 0.01%、Starlink-b 0.002%。
- **星座越大誤差越小**，因為 ISL 越短，走偏一點點的代價越小。

### 5.5 不規則拓樸（§V-D）
- **相位不均勻**（攝動造成衛星偏離名義位置，δu ~ N(0, σ²)，Fig. 12）：偏差在 1° 內時誤差 < 0.3%。文獻 [36] 顯示 Starlink 實際偏差大多 < 0.2°、最多 0.5°，所以實務上可用。
- **隨機鏈路故障**（Fig. 13）：Starlink 故障率 ≤ 0.1 時平均誤差 < 4%；72×22、5% 鏈路斷時只有 0.83%。72×22 比 24×66 好，因為軌道面多、跨軌 ISL 短，繞路代價小。
  - 注意：這裡 StepClimb **本身不會繞開故障**，所以這個「誤差」我理解為「照公式路徑走、遇到斷的鏈路再繞」的結果（論文說 "a detour happens"，但沒有寫明怎麼繞）。

### 5.6 Starlink 的 SDP 特徵（§V-E）
- Fig. 14：固定 M、N，SDP 長度會隨衛星移動（u0）而變。起點在 u0≈160°（大家都在低緯度）時最長；M=3、N=5 時變化幅度 9.26%，N=6 時增加到 15.80%。**跨軌越多，變化越大**。
- Fig. 15：(1,1)→(5,8) 的路徑形狀會變：
  - u0=45° 時，所有跨軌都在極區附近一次做完，路徑最短；
  - u0=145° 時，跨軌拆成兩段，各自在一個高緯度處（就是 bi-valley 的 bi-step）。
- 推論：如果大家都走最短路，**高緯度的衛星會承擔更多流量**，可能形成熱點。

## 6. Novelty／貢獻
1. **第一個 LEO SDP 的顯式解析解**：不建圖、不迭代，O(1)，輸入只要星座參數和兩端衛星的位置。
2. **把路長問題轉成「相位偏移」問題**，再化成一維中位數問題，數學上很乾淨。
3. **證明**了一個大家憑直覺在用的規則：跨軌要連續做，而且要在高緯度做（單谷有證明，雙谷有實驗支持）。這讓 DisCoRoute 一類的啟發式有了理論基礎。
4. 輸入需求小，作者認為可以**整合進分散式路由**（每顆衛星自己算，不需要全網拓樸）。

## 7. Limitations
1. **只看距離（傳播延遲）**：不考慮排隊、負載、頻寬。§V-E 自己也發現大家都走最短路會讓高緯度衛星變熱點，但沒有處理。
2. **假設拓樸完全規則**：Walker＋四 ISL、所有衛星同一套連線規則。相位偏差和鏈路故障只是事後量誤差，演算法本身**沒有處理故障的機制**。
3. **假設 ISL 一直都在**：這和 OPSPF 的假設**直接衝突**。OPSPF 在 |緯度|>70° 會**關掉跨軌 ISL**（極區斷線）；StepClimb 卻說高緯度的跨軌 ISL 最短、最該用。論文的 Monte-Carlo 傾角是 40°–70°，最高緯度 ≤ 70°，所以剛好避開這個問題。如果用在近極軌（如 Iridium 86.4°、OPSPF 的 LEO-48），就要另外處理極區關閉的鏈路（我的推論，論文沒討論）。
4. **seam（反向縫）沒有討論**：Walker Star 的第一個和最後一個軌道面方向相反，通常沒有跨軌 ISL。論文的模型是一般的 Walker＋四 ISL，沒有特別談 seam 怎麼處理（我的推論）。
5. **bi-valley 只是近似**：沒有證明，最差誤差 7.18%，最佳解機率約 78%。
6. **前提 SDP ⊂ MHP**：近極軌星座有少數例外 [20]，論文說實驗上仍可用。
7. **時間比較的公平性（我的推論）**：Table III 是「每組起終點各算一次」。實際上 Dijkstra 跑一次就能得到**同一個起點到所有終點**的最短路；如果要建整張路由表，差距會比表上小。不過對「只要一條路」或「分散式每顆衛星各自算」的情境，StepClimb 仍然有優勢。
8. **只給路徑，不給協定**：沒有講怎麼把結果裝進路由表、怎麼處理拓樸變化事件。這部分要和 OPSPF／StableRoute 那類「路由協定」搭配。

## 8. 與其他筆記的關聯
### 和 OPSPF 的關係
- **相同**：都利用「星座是規則、可預測的」，不靠 flooding 收集拓樸。OPSPF 用 GPS＋軌道預測建出拓樸，然後**還是跑 Dijkstra**（每秒一次）；StepClimb 進一步**連 Dijkstra 都省掉**，直接用公式。
- **可以互補**：OPSPF 的靜態模組（每秒一次 SPF）可以換成 StepClimb，計算更省；OPSPF 的動態模組（突發故障時用 OSPF Hello/LSU）剛好補上 StepClimb「不會處理故障」的缺點。
- **衝突**：OPSPF 在極區關掉跨軌 ISL；StepClimb 偏好在高緯度跨軌（見 §7 第 3 點）。
- **weight 不同**：OPSPF 沿用 OSPF 的 link cost；StepClimb 用實際公里數。

### 和 StableRoute 的關係
- StableRoute 的目標是**少換路**（讓路徑穩定，減少 TCP 受影響），用 weight=1（只算 hop）、用 next-hop set 和 Dijkstra 變形。
- StepClimb 的目標是**最短距離**，路徑會隨 u0 改變（Fig. 14/15：形狀和長度都在變）。所以**純用 StepClimb 反而會頻繁換路**，這正是 StableRoute 想解決的問題。
- 有趣的交集：StableRoute 的 next-hop set 本質上就是 MHP 區域內「往哪個方向走都還是最少 hop」的選擇；StepClimb 則是在同一個 MHP 區域裡**挑出距離最短的那一條**。可以想成：StableRoute 在 MHP 內挑「最穩」的，StepClimb 在 MHP 內挑「最短」的。

### 小對照表

| | OPSPF | StableRoute | StepClimb |
|---|---|---|---|
| 目標 | 快速收斂、少控制封包 | 少換路（路徑穩定） | 最短距離、算得快 |
| 怎麼算路 | 預測拓樸＋Dijkstra | next-hop set＋Dijkstra 變形 | **公式，不建圖** |
| weight | OSPF link cost | 1（hop） | 實際距離（km） |
| 處理突發故障 | 有（OSPF Hello/LSU） | 不是重點 | 沒有（只量誤差） |
| 極區 ISL | 關閉 | 依拓樸資料 | 假設一直在，還偏好用 |
| 有 problem formulation | 沒有 | 沒有 | **有**（式 (21)） |

### 其他
- **DoTD／LAMP**（拓樸設計）：決定「連哪幾顆」。StepClimb 假設固定的四 ISL +Grid；如果拓樸改成 DoTD 那種動態配對，StepClimb 的公式就不適用了。
- **DisCoRoute [26]、LSP [25]、DRA [27]**：本文的比較對象或前身，都是「在 MHP 區域裡走」的啟發式。DisCoRoute 是「在高緯度跨軌」的啟發式，StepClimb 等於幫它補上理論並修正誤差。
- **ref [20]**：證明 SDP ⊂ MHP，是本文的地基。
